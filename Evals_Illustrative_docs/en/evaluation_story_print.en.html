03Evaluation independence

ARAM takes the test. ARAM does not write its own answer key.

Every test case starts from one authoritative definition. From it, two things are produced separately: the documents ARAM is allowed to see, and the expected result, which ARAM never sees.

The expected result is derived independently from the frozen test-case definition and contract. The system under test never receives answer-key material.

Engineer's view
  • Oracle independence policy: a fixture/oracle component “must not import, call, copy algorithmic outputs from, or reuse the exact production implementation of the behavior it scores.” Every Route D oracle file declares sut_modules_imported: [], uses_tauri_predictions: false, uses_production_mapper_as_oracle: false, uses_production_extractor_as_oracle: false. Only shared primitives are allowed (ISO-8601 parser, SHA-256).
  • SUT isolation: never exposed to the SUT are fixture_spec.yaml, oracle/, golden approvals, expected labels/candidate IDs, forbidden-candidate lists, the validation report and hidden semantic tags. A leakage gate scans visible PDF text, PDF/XMP metadata, filenames, attachments, structured inputs and workspace paths.

Sources: TAURI_INTAKE_DATASET_AGENT_DESIGN.md §7.3, §34; EVALS_DATASET_AND_GROUND_TRUTH_DESIGN.md §16, §22; CASE-RD-06824/oracle/*.yaml.

04Separation of duties

One system runs the test. Another marks it.

Running a test and scoring it are separate responsibilities, handled by two separate components, so that the record of what ARAM did cannot be shaded by how it will be scored.

Test Harness

“Run the test, and record it.”

  • Checks the test case is eligible and its hashes match
  • Gives ARAM only the permitted inputs
  • Runs the real Intake behaviour
  • Captures a checkpoint at every layer
  • Captures reviewer actions
  • Preserves all run artefacts under a run manifest

It does not score.

Evaluation Harness

“Mark the test, and explain it.”

  • Validates the evaluation inputs
  • Compares expected vs actual
  • Calculates metrics with explicit numerator and denominator
  • Assigns a scoring status to every row
  • Classifies failures and finds their origin
  • Produces the reports and baseline comparisons

It does not run the product.

The Test Harness records what ARAM actually did. The Evaluation Harness independently decides how that behaviour is scored.

Engineer's view

Run modes (Test Harness §3): isolated, end_to_end, scripted_review (L5-A), interactive_review (L5-B). Every run writes a manifest (run_id, fixture_version, fixture_spec_hash, evaluation_contract_hash, intake_version, harness_version, injected_oracle_hashes, …). Scoring statuses and failure classification live only in the Evaluation Harness (§3, §12–14).

Sources: TAURI_INTAKE_TEST_HARNESS_DESIGN.md; TAURI_INTAKE_EVALUATION_HARNESS_DESIGN.md.

05Controls on the test itself

A test case has to earn the right to judge ARAM

Before a test case can count, it has to pass seven gates. Before it can become part of the golden set, people have to approve every critical fact and every piece of provenance.

Seven acceptance gates

G0Contract lock

The evaluation contract resolves and its hash matches; oracle independence is declared.

G1Fixture-spec integrity

Schema passes; critical-fact authority is valid; IDs are unique; states are coherent.

G2Source / build integrity

Required facts were injected exactly; no undeclared critical values slipped in.

G3Rendered evidence integrity

Every required piece of evidence exists on the rendered page and matches.

G4Mutation integrity

Any deliberate distortion (e.g. a scan artefact) is declared and its effect documented.

G5Oracle integrity

The answer key is compiled independently; human-only decisions are not guessed.

G6Isolation / replay / package

ARAM cannot see the answer key; the package is complete and replayable by hash.

Any mandatory gate failure removes the test case from product scoring. A broken test case cannot lower, or raise, ARAM's score.

Promotion ladder

GENERATED

Produced by the fixture generator. Not yet trusted.

VALIDATED_STRESS

Passed automated gates. Usable for stress testing.

GOLDEN

Every critical fact and its provenance reviewed and approved by people.

FROZEN_REGRESSION

Artefact hashes frozen. Admitted to regression testing.

“The agent cannot promote its own output.” Golden approval requires an evaluation engineer and a domain reviewer, with 100% review of critical (Tier-1) facts and 100% review of their provenance. Any change to a reviewed artefact's hash invalidates the approval.

Engineer's view
  • Gates G0–G6: Contract Lock · Fixture-Spec Integrity · Source/Build Integrity · Rendered Evidence Integrity · Mutation Integrity · Oracle Integrity · Isolation/Replay/Package Integrity.
  • Full ladder: GENERATED → VALIDATED_STRESS → evaluation-engineering review → domain plausibility review → 100% Tier-1 fact review → 100% Tier-1 provenance review → expected case/review-state approval → GOLDEN → frozen artifact hashes → FROZEN_REGRESSION.
  • Approval record approvals/golden_review.yaml, roles EVALUATION_ENGINEER and DOMAIN_REVIEWER. Compatibility states: ACTIVE_CURRENT, ACTIVE_LEGACY, DEPRECATED, QUARANTINED. Dataset splits: DISCOVERY, REGRESSION, HELD_OUT_VALIDATION, HUMAN_STUDY. “A fixture cannot silently change split.”
  • Tier-1 = a fact whose wrong value “can change route, gate, deadline, or verified-case correctness”.

Sources: EVALS_DATASET_AND_GROUND_TRUTH_DESIGN.md §9, §18, §20–21; TAURI_INTAKE_DATASET_AGENT_DESIGN.md §39, §41–42; TAURI_INTAKE_EVAL_REGRESSION_CI_DESIGN.md §10–11.

08The hard part of the test

The evaluation tests uncertainty, not just easy answers.

In this matter, the online tracking screen says “ZUGESTELLT” on 2026-04-20. There is no delivery record and no identified delivery person. A system that simply copied the date would manufacture a receipt date that the evidence does not support.

What the answer key expects

Receipt stays open, for a human to decide, instead of becoming a fact.

FieldExpected state (answer key)
delivery_methodCONFIRMED REGISTERED_MAIL
delivery_proofCONFIRMED false
termination_received_atREVIEW_REQUIRED null

Fails Silent choice

  • termination_received_at = 2026-04-20 taken from the tracking screen
  • delivery_proof = true
  • The conflict disappears from the case

Passes Preserve the uncertainty

  • Tracking date kept as a candidate, with its source
  • Receipt remains REVIEW_REQUIRED / unknown
  • Reviewer rejects the date and marks receipt unknown
  • Rejected candidate lineage retained

Important wording. This demonstrates tested system behaviour around evidence, uncertainty, provenance and review state. It does not show that any legal conclusion about receipt, deadlines or validity of a termination is correct.

Engineer's view
  • forbidden_candidates in oracle/l2_candidates.yaml: termination_received_at = 2026-04-20 (“Online tracking status is not authoritative proof of actual receipt in this fixture.”) and delivery_proof = true.
  • Evidence profile: ED-11 and EU-WF = PROVENANCE_INVALID / DEFECTIVE.
  • Invariants INV-D-004 and INV-D-005.
  • A silently discarded critical conflict is a zero-tolerance CI blocker.

10Where did it first go wrong?

A wrong final case is not enough information.

End-to-end testing shows that a case failed. Isolated testing gives each layer known-good input from the answer key, so each capability is measured on its own.

Layer under testReceives known-good inputWhat this isolates
L1Recovered text from the answer key
oracle/l0_recovery.yaml		Classification quality, independent of reading errors
L2Recovered text + correct classification
oracle/l0_recovery.yaml + oracle/l1_classification.yaml		Extraction quality, independent of reading and routing errors
L3Correct candidates + scripted reviewer decisions
oracle/l2_candidates.yaml + reviewer/scripted_actions.yaml		Transformation quality, independent of extraction and review errors
L4Correct transformed case state
oracle/l3_transformation.yaml		Structural validity, independent of upstream errors
L5Nothing injected: the complete workflow
full workflow		What a user actually experiences

End-to-end testing tells us that a case failed. Isolated testing helps identify which capability introduced the failure.

Root cause is assigned to the earliest causally sufficient divergence, found by walking the recorded lineage, not by assuming the earliest layer is to blame. Contributing causes are kept separately. For example: if L0 misreads a date and a reviewer then accepts it, the primary cause is L0 and HUMAN_REVIEW_ESCAPE is recorded as an additional cause.

Engineer's view

“These are compiled interfaces, not independently authored truth files. Every injected artifact is hash-pinned to the fixture manifest and evaluation-contract version” (Test Harness §5). Injected hashes appear in the run manifest as injected_oracle_hashes. “Report isolated layer quality separately from end-to-end observed quality” (L0–L5 design §6). Causal rule: “Do not infer causality from layer ordering alone” (§11).

11What if the evaluation itself is wrong?

A broken test must not be presented as a product failure.

Every scored row carries a status. Only rows marked SCORED enter a product metric. A defective test case, a contract gap or a harness crash is diagnosed separately and never becomes a zero in ARAM's score.

A real example: Route C

The Route C fixture's evaluation contract says certain social-selection evidence (EC-2 to EC-6) is always required. The underlying scenario, a complete closure, says social selection was unnecessary. Rather than invent a selection pool to satisfy the contract, the fixture marks the affected assertions as not scored until the contract owner resolves the gap (CG-001, with a second gap, CG-002).

route_c_2_AZR_276_16_dataset/oracle/l4_case_and_assertions.yaml → NOT_SCORED_CONTRACT_ERROR_FOR_AFFECTED_ASSERTIONS

In this baseline

All 240 jobs in golden-2026-09-25 were SCORED: nothing was excluded. Where a metric had nothing to measure, it is shown as “—”, not as 0%.

Engineer's view

Statuses: SCORED, NOT_APPLICABLE, NOT_SCORED_EXECUTION_ERROR, NOT_SCORED_CONTRACT_ERROR, NOT_SCORED_FIXTURE_DEFECT. “A fixture defect does not lower product metrics, but CI should fail the evaluation infrastructure job when a required regression fixture becomes unscorable.” Quarantine flow: mark NOT_SCORED_FIXTURE_DEFECT → exclude from denominators → move to QUARANTINED. “Do not assign product root-cause layers to unscorable fixtures.”

Sources: TAURI_INTAKE_EVALUATION_HARNESS_DESIGN.md §3, §13; TAURI_INTAKE_EVAL_REGRESSION_CI_DESIGN.md §7, §12; Route C README.md, fixture_spec.yaml (GENERATED_CONTRACT_REVIEW_REQUIRED), approvals/golden_review.yaml (PENDING_HUMAN_REVIEW).

12Reproducibility and regression protection

A discovered failure becomes a permanent regression check.

The evaluation produces replayable evidence, not one-off demonstrations. Every run is pinned to exact versions and hashes, so a result can be reproduced and a fix can be proven.

Evaluation finds a failure
Root cause identified
Product or test fixed
Same controlled case re-run
Failure proven fixed
Case frozen into regression
CI checks every future change

Three CI tiers

Pull request

Unit and contract tests, impacted-layer regression, safety fixtures, selected end-to-end smoke tests.

Main / release

Full regression suite, isolated L0–L4 evaluators, scripted L5-A cases, baseline delta report.

Release candidate

Frozen held-out evaluation, full end-to-end validation, and an L5-B real-human subset when human-workflow claims are made.

14Strengths, risks and interpretation

What the baseline shows, candidly

The harness is working as intended: it shows precisely where ARAM Intake is reliable today and where it is not yet ready.

Strong evidence

  • Critical Text Recovery Rate: 100.0% (404/404)
    Critical text recovered in every case.
  • Value Accuracy: 100.0% (212/212)
    When a fact is found, its value is right.
  • Conflict & Provenance Safety: 100.0% (204/204)
    Conflicts stayed visible; no silent overwrite.
  • Safe Rule Abstention Rate: 99.7% (617/619)
    Held back where rules required it (2 misses in 619).
  • Required-Field Completeness: 100.0% (486/486)
  • Evidence-State Validity: 100.0% (1,190/1,190)

Needs improvement

  • Verified Case Pass Rate: 2.5% (1/40)
    Only 1 of 40 cases passed strictly end-to-end.
  • Critical Error Escape Rate ↓: 63.0% (133/211)
    Of critical machine errors present at review entry, 63% were still wrong or unresolved at exit.
  • Classification Accuracy: 59.2% (197/333)
  • Wrong Rule-Pack Routing Rate ↓: 39.5% (150/380)
    Misrouted documents enter the wrong rule pack.
  • Fact Recall: 42.9% (188/438)
    Fewer than half of the expected facts were found.
  • Schema Pass Rate: 82.5% (33/40)
    7 of 40 cases failed schema validation.

Interpret carefully

  • Route D is 25 of 40 fixtures and dominates pooled values; Route B has 3.
  • Five metrics were not computed (no eligible units, or no single ratio). That is not the same as 0%.
  • No real-human (L5-B) data: reviewer effectiveness and correction burden are unmeasured.
  • The end-to-end review in this baseline is scripted (L5-A diagnostic computed for all 40 cases). Real reviewers may catch more, or fewer, errors.
  • Intake build, contract hash and harness version are not stated in the report.

Reading the layers in order shows a clear pattern: reading is clean, understanding and finding are the earliest weak layers, and the end-to-end result fails downstream.

15Scope of the claim

What this evidence does and does not establish

An assurance report is only as useful as its limits are clear.

Does establish

  • The answer key is independent of the system under test, and ARAM cannot see it.
  • The real Intake behaviour was exercised and its outputs captured at every layer.
  • Evidence provenance, conflicts, uncertainty and review states are part of the test.
  • Test-case defects cannot silently turn into product failures.
  • Runs are versioned and designed to be reproducible.
  • Baseline golden-2026-09-25 measured 40 synthetic German termination matters across four routes, with the results on pages 13–14.

Does not establish

  • That ARAM's output is legally correct, compliant or equivalent to a lawyer's work.
  • How real reviewers perform: no L5-B study is included.
  • Readiness for reliance without human review. At 2.5% strict end-to-end pass and 63.0% critical error escape, this baseline does not support that.
  • Performance on real, non-synthetic matters or on routes not in the dataset.
  • Any trend over time: this is the first baseline.

The purpose of the Evaluation & Testing Harness is not merely to produce a score. It creates reproducible evidence of what was tested, what ARAM actually did, how that compared with an independent expected result, where failures began, and whether a fix stays protected.

Fixture gates, promotion and independence

What a test case must pass before it can score ARAM.

GateGateChecks
G0Contract lockEvaluation contract resolves and hash matches; SUT compatibility contract resolves; one owner per namespace; oracle-independence declaration passes.
G1Fixture-spec integritySchema/constraints pass; Tier-1 authority valid; IDs unique and deterministic; fact/evidence/review states coherent.
G2Source / build integrityRequired assertions injected exactly; no undeclared critical values; retained source matches rendered input.
G3Rendered evidence integrityRequired evidence exists; artefact hash/page/span/slot resolve; rendered value matches the declared assertion.
G4Mutation integrityMutation class/recipe declared; anchor transformations explicit; semantic/evidence effects match the declaration.
G5Oracle integrityCandidate matching resolves; oracle independently compiled; human-required resolution not guessed; enough truth for the target metric.
G6Isolation / replay / packageHidden answer key not visible to the SUT; reproducibility contract passes; package complete and hash-consistent.

Independence rules

  • No fixture/oracle component may import, call, copy outputs from or reuse the production implementation of the behaviour it scores. Shared primitives are allowed only if they do not encode that behaviour.
  • The oracle compiler consumes only the contract, the frozen fixture_spec.yaml, renderer anchors, mutation lineage and human-approved resolution. “It must not consume Tauri predictions.”
  • “No scored Tier-1 fact may be accepted solely because an LLM generated it.” Authority must be DETERMINISTIC_SYNTHETIC, HUMAN_APPROVED_SYNTHETIC or HUMAN_RESOLUTION_REQUIRED.
  • Tier-2/3 material may be sampled for review only if it is not scored.
